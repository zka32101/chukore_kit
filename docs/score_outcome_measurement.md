# 本番の点の変化を測る設計（案）

コンセプト「気づいたら、点が上がっている。」が本当かを確かめるための設計。**本人が入力した本番の点**の変化を、端末内で見せ、必要なら匿名の統計だけを集める。

> ステータス: 案。**集計して外へ出す部分は、法務確認（子どもの学業成績の扱い、各国の個人情報、広告表示の根拠）が済むまで実装しない。** 数値は暫定で、結果を見る前に決めて記録する（[`global_rollout_criteria.md`](global_rollout_criteria.md)）。端末内で本人に見せる部分は、集めないので先に作れる。

## 1. 守ること

1. **本人の点は、本人の端末に置く。** 既定では送らない。
2. **見せる目的と、集める目的を分ける。** 端末内で「あなたの変化」を見せるのが先。集計は任意（オプトイン、保護者の同意）。
3. **点が上がらなくても責めない。** 入力は任意。入力しない選択を、普通のこととして扱う。
4. **約束しない。** 「上がる」とは言わず、「変化を一緒に確かめる」。結果の保証は、景表法・ストア規約に触れうる。
5. **自己申告は誤差が大きい**（盛る・入れない・テストごとに難しさが違う）と、最初から割り引く。

## 2. 何を測るか

| 層 | 見るもの | どこで |
|---|---|---|
| 本人向け | 本番の点の前回比・自己ベスト・到達レベルの変化 | 端末内（`compareRealTests` が既にある） |
| 運営向け（内部指標） | 点を入力した割合、点が上がった割合、変化の中央値、使った量との関係 | 匿名集計（法務のあと） |
| 対外（訴求） | 「使った人のうち◯%が点が上がったと入力」 | 最後。根拠・注記・法務確認のあとだけ（§7） |

## 3. 入力の取り方（端末内）

| タイミング | 内容 | 決まり |
|---|---|---|
| 使い始め（任意） | 「直近のテストの点」 | **使う前の基準**になる。無いと、使った効果と、ただ伸びただけを区別できない |
| テスト日を過ぎたあと | 「テストの点を入れる？」と1回だけ | `buildPostTestReview` の振り返りと同じ流れ。スキップできる。しつこく聞かない |
| 入力項目 | 点、満点、テストの種類（定期／模試／その他）、教科 | **満点を必ず持つ**（ブラジル 0〜10、トルコ 100 や LGS 500 など。比率 点÷満点 に直す） |

追加するもの（コード、集めない部分なので先に作れる）:
- `RealTestRecord` に `maxScore`（既定 100）と `kind` を足す。既存の呼び出しは壊さない。
- 満点の違いを吸収した `ratio`（0〜1）を返す。

## 4. 端末内で計算するもの（`buildOutcomeSummary`、案）

入力: 本番の点の記録、回答履歴。出力は**本人にだけ**見せる。

- 変化: 前回比、基準（使う前）からの変化、自己ベスト。比率で比べる（満点が違うテストを混ぜない）。
- 使った量: そのテストの前の期間の、学習日数・解いた問題数（`StudyDay` の学習日で数える）。
- 判定: 変化が**ノイズ幅（暫定 ±3点）以内**なら「ほぼ同じ」とする。「上がった」と言い切るのは、幅を超えたときだけ。
- 注意: 1回の差で喜びすぎない・落ち込ませない文面にする（責めない）。

## 5. 匿名で集める場合（法務のあと）

[`anonymous_data_collection.md`](anonymous_data_collection.md) の原則に従う。違いは、**点そのものは送らない**こと。

送る項目（1テスト1件、端末内で粗い区分にしてから）:

| 項目 | 区分 | 備考 |
|---|---|---|
| 変化の区分 | 5段階（大きく下がる／下がる／ほぼ同じ／上がる／大きく上がる） | 点は送らない |
| 基準の有無 | あり／なし | 基準なしは別に集計 |
| 使った量の区分 | 3段階（少／中／多） | 学習日数から端末内で決める |
| 教科・学年帯・地域（国） | | 学校名・地域（市区町村）は送らない |
| テストの種類 | 定期／模試／その他 | |

送らない: 点そのもの、満点、日付（月も）、学校、名前、端末ID、回答の中身。
集計側: 区分ごとの件数だけを保持し、**1セル 30 件未満は誰にも見せない**。個々の送信は保存しない。

## 6. 見方と落とし穴（内部指標）

| 落とし穴 | 内容 | 対処 |
|---|---|---|
| 入力した人だけの偏り | 点が上がった子ほど入れやすい | **入力率を必ず併記**する。入力率が低い（暫定 30% 未満）間は、結論を出さない |
| 平均への回帰 | 前回が悪かった子は、次に上がりやすい | 基準（使う前）のある子とない子を分けて見る |
| 使った量との関係 | 熱心な子ほど上がる（因果とは限らない） | 使った量の区分ごとに並べて示すが、「効果」とは書かない |
| テストの難しさ | テストごとに違う | 満点比に直し、同じ子の前後比較に限る。異なる子の絶対値は比べない |
| 他の要因 | 塾・家庭教師・成長 | 因果は言えない。言えるのは「使った人の入力では、こうだった」まで |

指標（暫定、結果を見る前に決める）:
- 入力率（テスト日を登録した子のうち、点を入力した割合）
- 「上がった」割合（ノイズ幅を超えて上がった割合）と、その信頼区間（`wilsonInterval` が使える）
- 変化の中央値、使った量の区分ごとの分布
- 判断に使う最小件数: 1セル 100 件以上（暫定）

## 7. 訴求に使う順序

1. **端末内の「あなたの変化」**（今すぐ可。集めない）。
2. **内部指標でコンセプトの検証**（法務のあと。ソフトローンチ）。
3. **対外の訴求**（最後）: 「使った人のうち◯%が点が上がったと入力（任意・自己申告、n=◯）」の形だけ。「上がる」「保証」は言わない。広告表示の根拠（合理的な根拠資料）と、国ごとの規制を法務で確認する。

## 8. 法務に聞くこと

- 子どもの学業成績（点の区分）を、匿名の統計でも集めてよいか。保護者の同意の取り方。
- 「使った人のうち◯%が点が上がった」の表現は、景表法・各国の広告規制で許されるか（根拠資料の水準）。
- ストアのデータ申告（成績の区分を送る場合の扱い）。
- 国ごとの年齢の線（韓国 14歳未満、ブラジル LGPD 第14条など）。

## 9. 作る順序

1. `RealTestRecord` に `maxScore`・`kind` を追加し、比率で比べる（互換テストつき）。
2. `buildOutcomeSummary`（端末内。変化・使った量・ノイズ幅）。
3. 振り返りの流れに「点の入力」を結ぶ（アプリ側の画面。基盤は文言と判定）。
4. 法務確認 → 匿名集計の送信用の変換（粗い区分にする関数。**送らない項目を落とすことをテストで固定**）。
5. 内部指標の集計表（`tool/` に置く、`quality_report.dart` と同じ形）。
